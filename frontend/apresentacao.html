1. Problema Identificado & Solução Proposta

O sistema de RPG de mesa Daggerheart utiliza mecânicas dinâmicas (Dados de Dualidade 2d12, Limiares Triplos de Dano, Slots de Armadura, Fadiga, 189 Cartas de Domínio e Contadores de Medo) que geram alta sobrecarga cognitiva em fichas de papel.

O Problema nas Mesas de RPG

  • Cálculo manual lento: converter dano bruto em Dano Menor (1 PV), Maior (2 PV) ou Grave (3 PV) atrasa o combate.
  • Falta de sincronia: o Mestre não consegue acompanhar PV, Fadiga e Armadura dos heróis nem gerenciar múltiplos encontros facilmente.
  • Metagame acidental: jogadores acabam vendo os pontos de vida e ataques secretos dos monstros do Mestre.

Nossa Solução Web (Daggerheart VTT)

  • Grimório & Ficha Oficial Digital: catálogo integrado com 10 classes, 18 ancestralidades, 9 comunidades e 189 cartas de domínio.
  • Campanhas com Múltiplos Combates Salvos: o Mestre cria campanhas, vincula personagens, mantém o Medo da campanha (0–10) e cria vários combates persistentes.
  • Segurança Real & Visão Anti-Metagame: autenticação JWT + Bcrypt onde a API oculta os atributos secretos dos monstros para jogadores.

Slide 2 de 8 • Arquitetura em Camadas

2. Como os Arquivos Conversam Entre Si

O projeto segue uma arquitetura modular em camadas. Toda ação do usuário percorre um caminho claro e seguro do navegador até o banco de dados relacional e volta como JSON:

1. HTML + CSS Tela visual, botões, inputs e modais
2. JS Front + Fetch Lê o DOM e envia requisição HTTP com Token JWT
3. server.js & Routes Recebe a URL + Método HTTP e direciona a rota
4. Middlewares Valida JWT (jwt.verify) e perfil do usuário
5. Controllers Aplica regras de negócio e monta query SQL
6. Database (SQL) Executa no MySQL / SQLite e retorna os dados

Por que separar em vários arquivos?

Separar Routes, Middlewares, Controllers e Database evita código espaguete, facilita a manutenção e garante que nenhuma consulta ao banco seja feita sem antes passar pela barreira de segurança do Middleware JWT.

Regra de Ouro da Segurança

O Front-end nunca acessa o banco de dados diretamente. Ele apenas faz pedidos HTTP via fetch() para a API Express, que valida quem é o usuário pelo Token JWT antes de executar qualquer operação.

3. Função dos Arquivos do Front-end

A pasta frontend/ contém a interface do usuário construída com HTML5 Semântico, CSS3 Moderno e JavaScript Puro (Vanilla ES6+):

Páginas HTML (.html)

  • index.html: Login, Cadastro de conta e Termo LGPD.
  • personagens.html: Grimório de heróis e modal da Ficha Oficial.
  • criar-ficha.html: Construtor guiado de novos personagens.
  • combate.html: Campanhas, múltiplos combates e Dados 2d12.
  • criaturas.html & admin.html: Bestiário do Mestre e Gestão de Contas.

Sessão & Navbar Global

  • auth.js: Salva o token JWT no localStorage e fornece a função apiFetch(url, options) que injeta automaticamente o cabeçalho Authorization: Bearer TOKEN em todas as requisições.
  • navbar.js: Renderiza a barra superior dinâmica (exibindo abas de Mestre/Pai conforme o perfil) e o modal de autoexclusão da LGPD.

Scripts de DOM (.js) & CSS

  • personagens.js, criar-ficha.js, combate.js, criaturas.js, admin.js: Fazem chamadas apiFetch() para a API e atualizam o DOM dinamicamente (innerHTML, eventos).
  • style.css: Define a paleta de cores (#9ECEFC, #FCE49F, #FCCA9F, #385C7D, #7D755E) e o layout responsivo.

Slide 4 de 8 • Camada Back-end (Pasta backend/)

4. Função de Routes, Middlewares, Controllers e Database

Cada subpasta do backend/ possui uma responsabilidade única e bem definida:

1. Routes (backend/routes/*.js)

O que fazem: São a "recepção" da API. Mapeiam o método HTTP (GET, POST, PUT, PATCH, DELETE) e o caminho da URL para a função correspondente do Controller.
Exemplo: campanhasRoutes.js define que POST /api/campanhas passa primeiro por authMiddleware e requireMestre antes de chamar criarCampanha.

2. Middlewares (backend/middlewares/*.js)

O que fazem: São os "seguranças" das rotas. Executam entre a Rota e o Controller.
Exemplo: authMiddleware.js lê o token JWT do header, valida a assinatura com jwt.verify(token, JWT_SECRET) e verifica se o usuário é Mestre (requireMestre) ou Conta Pai (requirePai). Se falhar, bloqueia na hora com erro 401 ou 403.

3. Controllers (backend/controllers/*.js)

O que fazem: São o "cérebro" do sistema. Recebem a requisição já autenticada (req.user, req.body), aplicam as regras de negócio (ex.: verificar se o jogador é dono da ficha, ocultar vida de monstros para players, criptografar senha com bcrypt) e chamam o banco de dados.

4. Database (backend/database/conexao.js)

O que faz: Gerencia a comunicação com o banco de dados relacional. Conecta ao MySQL via variáveis do .env (e possui fallback automático para SQLite local carregando sql/daggerheart.sql), expondo o método pool.query(sql, params) protegido contra SQL Injection.

Slide 6 de 8 • Segurança & Controle de Acesso

6. Perfis de Usuário, Bcrypt e JWT

As permissões não são apenas visuais: todas as regras de acesso são verificadas obrigatoriamente pela API no Back-end.

Jogador (player)

  • Cria, visualiza, edita e exclui apenas suas próprias fichas.
  • Participa dos combates das campanhas em que seu herói está vinculado.
  • Anti-Metagame: na arena, a API envia apenas o nome e a imagem dos monstros (ocultando PV, Fadiga e ataques).

Mestre (mestre)

  • Visualiza e gerencia as fichas de todos os jogadores da mesa.
  • Cria Campanhas, vincula heróis, controla a Barra de Medo da campanha (0 a 10) e cria múltiplos combates salvos.
  • Acesso total ao CRUD do Bestiário (129 criaturas oficiais + criação/edição).

Conta Pai (mumu) & Segurança

  • Acessa o painel admin.html para criar contas, alternar perfil (PUT /usuarios/:id/papel) e excluir usuários.
  • Bcrypt: senhas salvas com hash irreversível (bcrypt.hash) e nunca retornadas na API.
  • LGPD: direito ao esquecimento com autoexclusão em cascata.

Slide 7 de 8 • Modelagem Relacional & CRUD

7. Banco de Dados Relacional & CRUDs Integrados

O script sql/daggerheart.sql estrutura 11 tabelas relacionais com chaves primárias (PK), estrangeiras (FK) e integridade referencial (ON DELETE CASCADE):

Relacionamentos Principais do Banco

  • USUARIOS (1) ➔ (N) PERSONAGENS: cada ficha pertence a um usuário (USUARIO_ID).
  • USUARIOS (1) ➔ (N) CAMPANHAS: o Mestre cria campanhas que guardam os FEAR_POINTS.
  • CAMPANHAS (N) ➔ (N) PERSONAGENS: tabela associativa CAMPANHA_PERSONAGENS.
  • CAMPANHAS (1) ➔ (N) COMBATES: múltiplos combates salvos dentro da mesma campanha.
  • COMBATES (1) ➔ (N) COMBATE_HEROIS / COMBATE_CRIATURAS: combatentes ativos em cada encontro.

4 CRUDs Completos (POST, GET, PUT/PATCH, DELETE)

  • 1. Personagens (/personagens): Criar ficha, listar/filtrar, editar atributos/recursos/inventário/cartas e excluir.
  • 2. Campanhas & Combates (/api/campanhas e /api/combate): Criar campanhas e encontros, vincular heróis, sincronizar PV/PF/Armadura/Medo e remover.
  • 3. Bestiário (/api/criaturas): Consultar 129 monstros, cadastrar novos, editar em modal e deletar.
  • 4. Usuários (/api/auth/usuarios): Cadastrar, listar (sem senha), alterar papel e excluir conta.

Slide 8 de 8 • Guia de Defesa do Projeto

8. Resumo Rápido para Perguntas do Professor

Principais pontos técnicos para explicar o funcionamento do código durante a arguição da Entrega 4:

❓ "Qual a diferença entre Route, Middleware e Controller?"

• A Route (routes/*.js) apenas define o endereço da URL e o verbo HTTP.
• O Middleware (authMiddleware.js) intercepta o pedido antes do controller para validar o token JWT e checar se o perfil tem permissão.
• O Controller (controllers/*.js) executa a regra de negócio e faz a consulta SQL no banco.

❓ "Como o Front-end envia o Token JWT para o Back-end?"

No login (POST /api/auth/login), o servidor gera um token assinado com jwt.sign(). O front-end salva no localStorage e a função apiFetch() em auth.js envia esse token no cabeçalho HTTP Authorization: Bearer <token> em todas as requisições.

❓ "Como as senhas são protegidas no banco e na API?"

Usamos a biblioteca bcryptjs com 10 rounds de salt (bcrypt.hash no cadastro e bcrypt.compare no login). Além disso, o SELECT da rota GET /api/auth/usuarios nunca seleciona a coluna SENHA.

❓ "Quais são as principais regras de negócio implementadas?"

1. Sincronização automática de PV, Fadiga e Armadura entre a arena de combate e a ficha do personagem;
2. Pontos de Medo (0–10) persistidos por Campanha e incrementados automaticamente ao rolar "Com Medo" nos Dados de Dualidade 2d12;
3. Filtro anti-metagame no backend que oculta estatísticas dos monstros para contas de jogador.
